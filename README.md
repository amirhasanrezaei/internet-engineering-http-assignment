

**سوال ۱**

ورژن HTTP/0.9 اولین نسخه HTTP بود که فقط از متد GET پشتیبانی می‌کرد و هدر و کد وضعیت نداشت.

ورژن HTTP/1.0 هدرها، کدهای وضعیت و متدهایی مانند POST را معرفی کرد. در این نسخه معمولاً برای هر درخواست یک اتصال TCP جدید ایجاد می‌شد.

ورژن HTTP/1.1 امکان استفاده مجدد از اتصال TCP را فراهم کرد. همچنین هدر Host، قابلیت‌های بهتر کش و انتقال داده به روش Chunked را معرفی کرد.

ورژن HTTP/2 از قالب دودویی به‌جای قالب متنی استفاده می‌کند و با قابلیت Multiplexing امکان ارسال چند درخواست و پاسخ از طریق یک اتصال TCP را فراهم می‌کند. همچنین از فشرده‌سازی هدرها با HPACK استفاده می‌کند.

ورژن HTTP/3 از پروتکل QUIC روی UDP استفاده می‌کند. این نسخه با کاهش تأخیر، پشتیبانی از جریان‌های مستقل و استفاده از TLS 1.3 ارتباط سریع‌تر و امن‌تری فراهم می‌کند.

در HTTP/3 به‌جای استفاده مستقیم از TCP، از پروتکل QUIC استفاده می‌شود که روی UDP اجرا می‌شود. UDP یک رابط انتقال سبک فراهم می‌کند و به QUIC اجازه می‌دهد قابلیت‌هایی مانند ارسال مطمئن داده‌ها، کنترل ازدحام، رمزنگاری و مدیریت جریان‌ها را پیاده‌سازی کند. یکی از مزایای مهم این روش آن است که ازدست‌رفتن بسته‌های مربوط به یک جریان لزوماً مانع دریافت داده‌های جریان‌های دیگر نمی‌شود. این ویژگی مشکل مسدودشدن جریان‌ها را که در HTTP/2 روی TCP وجود دارد، کاهش می‌دهد. همچنین QUIC از TLS 1.3 استفاده می‌کند و امکان تغییر شبکه، برای مثال جابه‌جایی از Wi-Fi به اینترنت همراه، را بهتر فراهم می‌کند. البته دلیل استفاده از UDP این نیست که UDP به‌خودی‌خود از TCP مطمئن‌تر یا امن‌تر است؛ بلکه QUIC قابلیت‌های لازم برای انتقال مطمئن و امن را روی UDP پیاده‌سازی می‌کند..

**سوال 2**

الف) در ارتباط Stateless، هر درخواست به‌صورت مستقل پردازش می‌شود و سرور برای پردازش درخواست جدید به خاطر سپردن درخواست‌های قبلی وابسته نیست. اطلاعات لازم برای پردازش درخواست باید در خود درخواست موجود باشد یا از منبع دیگری دریافت شود. در مقابل، در ارتباط Stateful، سیستم اطلاعاتی درباره تعاملات قبلی یا وضعیت فعلی ارتباط نگهداری می‌کند. در این حالت، درخواست‌های بعدی می‌توانند به اطلاعات ذخیره‌شده در مراحل قبلی وابسته باشند.

ب) پروتکل HTTP در اصل یک پروتکل Stateless است؛ یعنی هر درخواست می‌تواند مستقل از درخواست‌های قبلی پردازش شود و خود پروتکل الزام نمی‌کند که سرور وضعیت درخواست‌های گذشته را نگهداری کند. با این‌ حال، برنامه‌های تحت وب معمولاً به نگهداری اطلاعاتی مانند وضعیت ورود کاربر، سبد خرید و تنظیمات شخصی نیاز دارند. برای این کار از روش‌هایی مانند Cookie، شناسه نشست یا Session ID، ذخیره‌سازی نشست در سمت سرور و توکن‌هایی مانند JWT استفاده می‌شود. برای مثال، وب‌سایت می‌تواند شناسه نشست کاربر را در قالب Cookie به مرورگر ارسال کند. مرورگر این شناسه را در درخواست‌های بعدی می‌فرستد و سرور با استفاده از آن، اطلاعات نشست مربوط به کاربر را بازیابی می‌کند. بنابراین، اگرچه HTTP در سطح پروتکل Stateless است، برنامه‌های مبتنی بر آن می‌توانند رفتار Stateful داشته باشند

**سوال 3**

الف) در مدل معمول ارتباط HTTP، کلاینت درخواست را آغاز می‌کند و سرور در پاسخ به آن اطلاعات ارسال می‌کند. سرور معمولاً نمی‌تواند بدون وجود یک سازوکار ارتباطی که کلاینت ایجاد کرده است، هر زمان که بخواهد پاسخ HTTP جدیدی را برای کلاینت ارسال کند. این موضوع برای برنامه‌هایی که به دریافت اطلاعات لحظه‌ای نیاز دارند، مانند پیام‌رسان‌ها، سیستم‌های اعلان، هشدارها و Webhookها، مشکل ایجاد می‌کند. برای مثال، در یک برنامه چت ممکن است کاربر جدیدی برای کاربر دیگری پیام ارسال کند، درحالی‌که کاربر دوم درخواست جدیدی به سرور نفرستاده است. برنامه باید روشی برای رساندن سریع پیام به کاربر دوم داشته باشد.

ب)  
1. Polling

در روش Polling، کلاینت در فواصل زمانی مشخص درخواست HTTP ارسال می‌کند تا بررسی کند آیا اطلاعات جدیدی وجود دارد یا خیر. برای مثال، برنامه چت می‌تواند هر پنج ثانیه درخواست جدیدی برای دریافت پیام‌ها ارسال کند. پیاده‌سازی این روش ساده است و با زیرساخت معمول HTTP کار می‌کند؛ اما ممکن است درخواست‌های غیرضروری زیادی ایجاد کند و دریافت اطلاعات جدید تا زمان ارسال درخواست بعدی به تأخیر بیفتد.

۲. Long Polling

در روش Long Polling، کلاینت درخواست خود را ارسال می‌کند و سرور تا زمان آماده‌شدن اطلاعات جدید یا پایان مهلت انتظار، درخواست را باز نگه می‌دارد. سپس پاسخ ارسال می‌شود و کلاینت درخواست دیگری ایجاد می‌کند. این روش در مقایسه با Polling معمولی می‌تواند تعداد درخواست‌های غیرضروری را کاهش دهد و اطلاعات را سریع‌تر منتقل کند؛ اما همچنان به ارسال درخواست‌های تکراری نیاز دارد و ممکن است منابع سرور را مصرف کند.

۳. WebSocket

وب سوکت یک کانال ارتباطی پایدار و دوطرفه بین کلاینت و سرور ایجاد می‌کند. پس از برقراری اتصال، هر دو طرف می‌توانند بدون نیاز به ایجاد درخواست جدید برای هر پیام، اطلاعات ارسال کنند. این روش برای برنامه‌های چت، بازی‌های چندنفره و سیستم‌های تعاملی که به ارتباط لحظه‌ای و دوطرفه نیاز دارند، بسیار مناسب است. از چالش‌های آن می‌توان به مدیریت اتصال‌های طولانی‌مدت، احراز هویت، مقیاس‌پذیری و سازگاری با زیرساخت شبکه اشاره کرد.

۴. Server-Sent Events یا SSE

در روش Server-Sent Events، سرور می‌تواند از طریق یک اتصال HTTP طولانی‌مدت، رویدادها و اطلاعات جدید را به‌صورت پیوسته برای کلاینت ارسال کند. این روش برای اعلان‌ها، داشبوردهای زنده، سیستم‌های مانیتورینگ و نمایش اخبار لحظه‌ای مناسب است؛ زیرا در این کاربردها بیشتر به ارسال اطلاعات از سرور به کلاینت نیاز داریم. برخلاف WebSocket، روش SSE یک کانال عمومی ارتباط دوطرفه فراهم نمی‌کند و کلاینت برای ارسال اطلاعات به سرور معمولاً باید از درخواست‌های HTTP جداگانه استفاده کند.

۵. Webhook

در روش Webhook، یک برنامه هنگام وقوع رویدادی مشخص، درخواست HTTP را به آدرس از پیش تعیین‌شده برنامه دیگری ارسال می‌کند. برای مثال، پس از موفقیت‌آمیز بودن پرداخت در یک درگاه پرداخت، آن سرویس می‌تواند یک درخواست Webhook برای فروشگاه اینترنتی ارسال کند تا فروشگاه از نتیجه پرداخت مطلع شود. این روش برای ارتباط رویدادمحور بین سرویس‌های سمت سرور بسیار مناسب است؛ زیرا سرویس دریافت‌کننده لازم نیست مرتباً از سرویس ارسال‌کننده درباره وضعیت رویداد سؤال کند. برای استفاده مطمئن از Webhook باید مواردی مانند اعتبارسنجی امضای درخواست، تلاش مجدد در صورت شکست و جلوگیری از پردازش تکراری رویدادها در نظر گرفته شوند.

**سوال 4**

آدرس داده‌شده:

ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1

Scheme: ss

Username: asghar

Password: 1234!!

Host: ss.myproxy.com

Port: 1234

Fragment: shadowSocks1

اScheme نوع آدرس را مشخص می‌کند. Username و Password بخش اطلاعات کاربر هستند. Host نام میزبان سرور و Port شماره درگاه آن است. Fragment نیز بخشی است که پس از علامت # قرار می‌گیرد و می‌تواند برای مشخص‌کردن نام یا توضیحات یک پیکربندی استفاده شود.

**سوال 5**

۱. اگر پایگاه داده وب‌سایت دچار اختلال موقت شده و درخواست‌های ورود قابل پردازش نباشند، کد 503 Service Unavailable مناسب است. اگر خطای داخلی غیرمنتظره‌ای رخ داده باشد، کد 500 Internal Server Error نیز می‌تواند استفاده شود.

۲. اگر ورود کاربر به دلیل نامعتبر بودن اطلاعات احراز هویت ناموفق باشد، کد 401 Unauthorized مناسب است. بهتر است سامانه مشخص نکند که نام کاربری اشتباه بوده یا رمز عبور.

۳. اگر وب‌سایت به دامنه دیگری منتقل شده باشد، کد 301 Moved Permanently مناسب است. آدرس جدید باید در هدر Location قرار گیرد. اگر لازم باشد متد درخواست حفظ شود، می‌توان از کد 308 Permanent Redirect استفاده کرد.

۴. اگر تعداد درخواست‌های کاربر از حد مجاز بیشتر شود، کد 429 Too Many Requests مناسب است. سرور می‌تواند از هدر Retry-After برای مشخص‌کردن زمان ارسال درخواست بعدی استفاده کند.

۵. اگر درخواست تمدید JWT موفق باشد و توکن جدید در هدر پاسخ قرار بگیرد، کد 200 OK مناسب است. اگر پاسخ عمداً بدنه نداشته باشد، کد 204 No Content نیز می‌تواند استفاده شود.

۶. اگر دسترسی کاربر به دلیل قرارگرفتن IP او در محدوده ممنوع‌شده رد شود، کد 403 Forbidden مناسب است. این کد نشان می‌دهد که سرور درخواست را درک کرده، اما اجازه دسترسی نمی‌دهد.

**سوال 6**

سناریوی اول: استفاده از سرورهای داخلی دانشگاه به‌جای سرورهای مرکزی برای دریافت بسته‌های نرم‌افزاری

نوع پیشنهادی: Forward Proxy یا Caching Proxy

پروکسی رو به جلو یا Forward Proxy از طرف کلاینت‌ها به سرورهای خارجی درخواست ارسال می‌کند. در شبکه دانشگاه، این پروکسی می‌تواند درخواست دانلود بسته‌های نرم‌افزاری را دریافت کرده و بسته‌ها را از مخازن خارجی دریافت کند. اگر پروکسی قابلیت کش داشته باشد، بسته‌های دانلودشده را ذخیره می‌کند تا کاربران دیگر بتوانند همان بسته‌ها را بدون دانلود مجدد از اینترنت دریافت کنند. این کار باعث کاهش مصرف پهنای باند و افزایش سرعت دانلود می‌شود. راهکار دیگر استفاده از Repository Mirror است. در این روش، دانشگاه یک نسخه محلی از مخازن نرم‌افزاری، مانند مخازن Ubuntu، نگهداری می‌کند. البته Repository Mirror و Forward Proxy دقیقاً یکسان نیستند؛ اما هر دو می‌توانند وابستگی به سرورهای خارجی را کاهش دهند.

سناریوی دوم: تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی آن‌ها

نوع پیشنهادی: Reverse Proxy یا Load Balancer با قابلیت مسیریابی جغرافیایی

پروکسی معکوس یا Reverse Proxy درخواست‌های کاربران را دریافت کرده و آن‌ها را به سرورهای مناسب ارسال می‌کند.

اگر قابلیت مسیریابی جغرافیایی داشته باشد، می‌تواند درخواست‌های کاربران را بر اساس موقعیت جغرافیایی به سرورهای نزدیک‌تر هدایت کند. برای مثال، درخواست‌های کاربران اروپایی به سرورهای اروپا و درخواست‌های کاربران آسیایی به سرورهای آسیا ارسال می‌شوند. این روش می‌تواند تأخیر ارتباط را کاهش دهد و توزیع بار را بین سرورهای مختلف بهبود ببخشد. مسیریابی جغرافیایی همچنین می‌تواند با استفاده از DNS یا شبکه توزیع محتوا (CDN) انجام شود؛ بنابراین، روش دقیق پیاده‌سازی به زیرساخت مورد استفاده بستگی دارد.

سناریوی سوم: اضافه‌کردن قابلیت احراز هویت به یک سرویس قدیمی

نوع پیشنهادی: Reverse Proxy یا Authentication Gateway

در این روش، یک پروکسی معکوس یا درگاه احراز هویت در مقابل سرویس قدیمی قرار می‌گیرد و درخواست‌ها را پیش از رسیدن به سرویس بررسی می‌کند. برای مثال، درگاه احراز هویت می‌تواند اعتبار توکن یا اطلاعات کاربر را بررسی کند و فقط درخواست‌های مجاز را به برنامه قدیمی ارسال کند. با این روش می‌توان قابلیت احراز هویت را بدون ایجاد تغییرات گسترده در کد برنامه قدیمی اضافه کرد. البته باید از دسترسی مستقیم و غیرمجاز به سرویس پشتیبان جلوگیری شود و اطلاعات هویتی کاربران نیز به‌صورت امن مدیریت شوند.

اعلام استفاده از هوش مصنوعی: در انجام این تمرین از ChatGPT با مدل GPT-6 کمک گرفتم. از آن برای یادگیری و درک بهتر مفاهیم پروتکل HTTP، نسخه‌های مختلف آن، کدهای وضعیت HTTP و نحوه استفاده از پراکسی‌ها کمک گرفتم. همچنین برای بررسی و درک بهتر پاسخ سؤالات تمرین از آن استفاده کردم.
